### Inventory Interpretation

- Moodle row identity is `source=Moodle`, `interface=database XMLDB`, logical table `entity`, and exact column `field`. Actual physical table prefixes are deployment configuration; do not hard-code `mdl_`.
- `type` and `length` preserve XMLDB declarations such as `int`, `char`, `number`, `text`, and `10,5`. XMLDB types are database-independent and are not assumed PostgreSQL/MySQL physical types.
- `nullable=false` comes only from `NOTNULL="true"`; `nullable=true` comes only from `NOTNULL="false"`; absent declaration is `unknown`. SQL nullability is not REST field presence or API nullability.
- `default` preserves an explicitly declared `DEFAULT`; otherwise it is `unknown`, not an inferred null or zero. Empty strings remain empty CSV cells. The inventory does not include every XMLDB attribute such as `SEQUENCE` or every index definition; consult its source URL for those.
- `keys` captures declared primary/unique/foreign keys involving the field, including composite fields and reference targets. It does not claim all XMLDB relationships are physically enforced in every database, nor does it enumerate every implicit/application join or index.
- `version` is `v5.0.2@e27e1ed7bc33f9a7b1820c165133dd585d5c27db`; `evidence_sha256` hashes the downloaded XML bytes. No raw source archive, script, or database records were written into the workspace.
- Complete inventory means all **non-test install.xml table/field declarations in this pinned official repository**, not every possible table after upgrades or installation of additional plugins. The [BigBlueButton test extension fixture](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/mod/bigbluebuttonbn/tests/fixtures/extension/simple/db/install.xml) declares `bbbext_simple` with five fields; it was discovered and parsed but deliberately excluded from the CSV. Compare the deployed version, plugin schemas, upgrade code, and approved actual DDL before freezing a production contract.
- This full metadata inventory includes sensitive fields such as `user.password` and `user.secret`. It is not an extraction allowlist. Never include password hashes, secrets, access tokens, or session data in an education analytics extract.

## Completion And Engagement Storage

[Core XMLDB](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/lib/db/install.xml) declares these completion tables:

- `course_modules_completion`: **all fields** `id`, `coursemoduleid`, `userid`, `completionstate`, `overrideby`, `timemodified`. `coursemoduleid` joins the course module. There is no `CompletionPercent`, `ViewsCount`, or time-on-task column here.
- `course_completions`: **all fields** `id`, `userid`, `course`, `timeenrolled`, `timestarted`, `timecompleted`, `reaggregate`. Completion criteria and criterion completion are separately stored in `course_completion_criteria` and `course_completion_crit_compl`; aggregation rules also matter.
- `user_lastaccess` and `user.lastaccess` are summary observations, not event inventories. Latest access cannot reconstruct counts, sessions, or an attendance register.

The standard log store has its own [XMLDB schema](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/admin/tool/log/store/standard/db/install.xml). **All 21 `logstore_standard_log` fields** are: `id`, `eventname`, `component`, `action`, `target`, `objecttable`, `objectid`, `crud`, `edulevel`, `contextid`, `contextlevel`, `contextinstanceid`, `userid`, `courseid`, `relateduserid`, `anonymous`, `other`, `timecreated`, `origin`, `ip`, `realuserid`.

Treat `id` as log-row identity within the site/store, `timecreated` as event time, and `eventname`/`component`/`action`/`target` as event classification. `objectid` is polymorphic through `objecttable`; it is not always a content ID. Context instance is also polymorphic. `userid`, `relateduserid`, and `realuserid` describe different actors/relationships, particularly impersonation and system actions. Do not assign system/anonymous events to a guessed student.

`other` is event-specific encoded detail, not a stable cross-event object schema. Log tables provide no universal reliable active-duration field. Deriving sessions from gaps between timestamps requires a documented cap, timeout, exclusion of background/system events, timezone, confidence, and estimation flag. Missing events can reflect log configuration or retention, not student inactivity. Completion is not necessarily mastery, and a course-progress percentage is not a per-content percentage.

## External Functions Are A Different Interface

The REST transport is the tenant's `/webservice/rest/server.php`, with function selection through `wsfunction` and JSON selection through `moodlewsrestformat=json`; use approved credentials via the site's supported secure request pattern. This transport is implemented by the release's [REST server](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/webservice/rest/server.php). Do not put tokens into saved example URLs, source control, notebook output, or telemetry.

Enabling the REST protocol does not expose every PHP function. Functions must be registered, included in the token's enabled service, and authorized for the caller and context. The [core service registry](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/lib/db/services.php) is a reference, not the tenant's enabled-function list. Functions marked for AJAX or a mobile service are not automatically authorized by an arbitrary external-service token.

Types below are PHP external API declarations such as `PARAM_INT`, `PARAM_FLOAT`, `PARAM_BOOL`, `PARAM_RAW`, `PARAM_TEXT`, `PARAM_URL`, and `PARAM_PLUGIN`; they are not database types. `VALUE_OPTIONAL` means a key may be absent, not that its value is nullable. `VALUE_DEFAULT` describes defaults; explicit `NULL_ALLOWED` or the relevant constructor/exporter determines null acceptance. Unless specifically established for the return declaration, API nullability remains **unknown**. The relevant [external_value class](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/lib/external/classes/external_value.php) is part of the pinned evidence.

### Assignment And Grade Responses

The exact implementation and declarations are in [mod/assign/externallib.php](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/mod/assign/externallib.php). Function names are carried in `wsfunction`, not paths such as `/api/assignments`.

- `mod_assign_get_assignments`: course-scoped assignment discovery. Use returned assignment instance IDs and course-module context; do not assume database columns or all assignments in the site are visible to the token.
- `mod_assign_get_submissions`: response `assignments[].assignmentid`, `assignments[].submissions[]`, and `warnings[]`. `assignmentid` is declared `PARAM_INT`; nested fields are defined by `get_submission_structure()`. Selected nested fields include `id`, `userid`, `attemptnumber`, `status`, `timecreated`, `timemodified`, `groupid`, and plugin data. This API wrapper uses **`assignmentid`**, while the database column is **`assign_submission.assignment`**.
- `mod_assign_get_grades`: `assignments[].assignmentid`, `assignments[].grades[]`, `warnings[]`; nested grades come from `get_grade_structure()`. Preserve `userid`, attempt context, numeric/display representation as actually declared, grader and timestamps where returned. Warnings can represent no grades or lack of permission; neither is automatically an empty successful result.
- `mod_assign_get_user_flags`: `assignments[].assignmentid` and user flags with `id`, `userid`, `locked`, `mailed`, `extensionduedate`, `workflowstate`, `allocatedmarker`. The integer fields use `PARAM_INT`; `workflowstate` is optional `PARAM_ALPHA`. Extensions and marking workflow belong in the extraction contract.
- `mod_assign_get_submission_status`: a user-context status response, including submission/feedback/history-related structures according to its declaration and access. Do not assume `get_submissions` is a full append-only attempt audit; test reopened and team submissions and older attempts explicitly.
- Do not call assignment `view_*`, save, grade, submit, reveal-identity, lock, or completion-update functions for a passive pull. Several seemingly observational view functions generate events and would contaminate engagement measurements.

Gradebook response evidence comes from the [grade-report registry](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/grade/report/user/db/services.php) and [gradereport_user external class](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/grade/report/user/classes/external/user.php).

`gradereport_user_get_grade_items` returns `usergrades[]` with `courseid`, `courseidnumber`, `userid`, `userfullname`, `useridnumber`, `maxdepth`, and `gradeitems[]`. Selected grade-item response fields are `id`, `itemname`, `itemtype`, `itemmodule`, `iteminstance`, `itemnumber`, `categoryid`, `outcomeid`, `scaleid`, `cmid`, `graderaw`, `grademin`, `grademax`, `gradeformatted`, `percentageformatted`, `lettergradeformatted`, `gradedatesubmitted`, `gradedategraded`, `gradeishidden`, `gradeislocked`, `gradeisoverridden`, `gradeneedsupdate`, `status`, `feedback`.

`graderaw`, `grademin`, and `grademax` are declared `PARAM_FLOAT`; flags such as `gradeishidden` are `PARAM_BOOL`; `gradeformatted` is `PARAM_RAW`. **`graderaw` is not a database column named `rawgrade` in this response.** Formatted percentages/letters can contain presentation text and must not be the primary numeric source. Registration references `gradereport/user:view`, but runtime checks, grade visibility, group restrictions, and ability to view other users still matter. A course total grade item belongs in a proposed course-grade entity.

## Missing Work, Grade Semantics, And Time

1. **Assignment audience first:** determine active enrollment, activity availability, group/grouping access, hidden/deleting module status, and applicable user/group overrides before generating expected work. No submission row does not itself mean missing work.
2. **Effective date precedence is implementation-specific:** [assign::update_effective_access and override_exists](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/mod/assign/locallib.php) select a matching group override ordered by `sortorder ASC`, then merge the user override; only set values are applied to the activity instance. The nearby comment refers to a "most lenient combination," but the inspected executable group lookup selects one ordered record. Preserve `sortorder`, null/zero semantics, and `assign_user_flags.extensionduedate`, and validate effective dates against Moodle instead of reimplementing the comment. Quizzes have their own override logic.
3. **Submission status is not completion:** draft, submitted, reopened, and group states differ. `latest` is a current-pointer flag; older attempts and grade updates need separate preservation. `timemodified` can reflect edits other than submission, so it is not a universal exact `SubmittedDate`. Leave unverified submission-event time unknown or use an explicitly approved event/status source.
4. **Grade and denominator:** preserve grade-item type, raw/final/overridden/hidden/excluded state, scale, bounds, grade-pass threshold, and course aggregation. A negative scale reference or display grade is not points. Derive a percentage only when a meaningful numeric scale and denominator have been established; retain raw score and rule version. Do not assume the same conversion for quiz raw marks, normalized quiz grade, and course total.
5. **Preview, incomplete, review-hidden, and ungraded attempts:** distinguish them. Do not turn API-suppressed marks into zero, treat unfinished attempts as failed completed assessments, or use the deprecated compatibility function for precise state analytics.
6. **Unix time and sentinels:** documented external timestamp fields use integer Unix times; convert to UTC while retaining raw values and site/user timezone for local reporting. Zero can mean not set/not finished. Course relative-date mode, user extensions, time limits, and activity availability affect due-date interpretation.
7. **Completion:** use enabled tracking and configured criteria; manual overrides and pass/fail completion states need explicit meaning. A completion ratio is derived with a recorded denominator, not an invented source column. `IsCompleted` does not imply proficiency or a passing assessment.
8. **Engagement:** distinguish event rows, course aggregates, last-access summaries, completion snapshots, and estimated sessions. Do not combine those grains under a single undifferentiated `DigitalEngagement` row. Teacher/system/impersonated events need actor classification, not automatic attribution to a student.

## Pagination, History, Access, And Retention

- Moodle has no universal Canvas-style `Link` pagination for all external functions. Read each function's parameters. The enrolled-user function supports paging options such as `limitfrom` and `limitnumber`; course, assignment, completion, and quiz functions have their own ID arrays, filters, or finite per-course results. Do not append guessed `page` or `per_page` parameters to all calls.
- Batch course/user/assignment IDs according to supported contracts and server limits. Record deterministic batch membership and reconcile source counts; offset paging through a changing roster can duplicate or miss users. Capture `warnings[]` and error bodies even when the transport succeeds.
- Capabilities are evaluated by context. Enrollment alone, a role shortname, a mobile-service registration, or inclusion in the service is not sufficient proof that a token can see hidden activities, other users, grades, groups, anonymous identities, or quiz review data.
- There is no established universal external-function CDC or deletion feed for this scope. `timemodified` exists only on some tables and changes do not propagate across all joins. Use object-specific refreshes, overlapping windows, current-key reconciliation, periodic snapshots, and explicit source/visibility status.
- For an approved database export, watermark each table according to its actual columns. A time-only cursor can miss equal-timestamp changes; use stable keys and overlap. Avoid assuming a log `id` watermark represents all late-imported or externally stored activity. Confirm transaction/replica consistency and deletion handling.
- [Standard log settings](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/admin/tool/log/store/standard/settings.php) declare `logstore_standard/loglifetime` and `logstore_standard/logguests`. [The cleanup task](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/admin/tool/log/store/standard/classes/task/cleanup_task.php) interprets positive lifetime in days; empty/negative lifetime returns without this cleanup. Source default zero is not evidence that a tenant keeps logs forever: alternate stores, administrator changes, privacy deletion, or operational purges may apply.
- [Server settings](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/admin/settings/server.php) include `disablegradehistory` and `gradehistorylifetime`. [Grade-history cleanup](https://raw.githubusercontent.com/moodle/moodle/e27e1ed7bc33f9a7b1820c165133dd585d5c27db/lib/classes/task/grade_history_cleanup_task.php) uses the configured lifetime in days. Current grades cannot reconstruct purged or disabled history.
- Snapshot role/group/cohort memberships, effective dates, grade settings, assignment audiences, completion, and content versions where historical attribution is needed. Current group membership is not reliable evidence of a learner's team at an older submission time.
- Retention acceptance must record active log-store plugins, source settings, scheduled-task health, earliest retrievable record per store/table/function, backups, deletion process, grade-history settings, and approved analytics retention. These were not verified against any tenant.

### Proposed Gaps And Priority

1. **Identity and academic context:** explicit identifiers with site/type/effective dates; school/catalog course/class/term crosswalk; context-aware role assignments. Do not solve classroom-section coverage by relabeling Moodle topics.
2. **Assignment / Audience / Override / Extension:** preserve source activity and course-module IDs, group/user targets, priority, dates, attempts, submission mode, marking workflow, and resolved per-learner availability. The workbook's single `LearningContent.DueDate` is insufficient.
3. **SubmissionAttempt / GroupSubmissionMember / GradeRevision / CourseGradeSnapshot:** separate group ownership, learner attribution, latest flag, attempt, raw/final/visible grade, denominator, scale, posted/released state where available, and configuration/history provenance.
4. **AssessmentAdministration / AssessmentResultComponent:** retain quiz attempt, question usage, item slot/version, state, marks/fractions, feedback visibility, and aggregate grade separately. Add competency/outcome components with scale semantics instead of forcing them into percentage/growth columns.
5. **LearningStandard / ContentStandardAlignment:** model frameworks, hierarchy/version, module/course alignment, proficiency scale, and evidence. Keep competencies distinct from gradebook outcomes until an approved taxonomy crosswalk exists.
6. **ContentVersion / ContentPlacement / CompletionSnapshot / EngagementGrain:** course sections are content containers; completion and logs need separate identities, timestamps, granularity, and derivation metadata.
7. **External/platform needs:** instructional calendar, official attendance, verified guardianship/support relationships, accommodations, demographics, intervention owner/outcome metrics, consent/legal basis, suppression/deletion, and immutable ingestion lineage remain outside these source guarantees.

## Corrections, Blockers, And Validation

- Existing research remains unchanged. Its Moodle `Section` and `ContentUsage` coverage should be understood as conditional: topics are not roster sections, and neither completion tables nor generic logs provide a universal duration/percentage/quality score.
- Database schemas are now grounded in a named immutable release, rather than conceptual field guesses. This raises confidence in the **reference storage schema**, not in an enabled tenant API or a hosted database extraction right.
- Enrollment and role assignment are confirmed separate relationships. An enrolled-user API list does not expose every `user_enrolments` row, plugin, start/end time, or effective role context.
- Assignment due-date precedence must follow the executable implementation, including ordered group overrides and extensions, rather than a generic latest-date/most-lenient heuristic. The inspected comment and code are not interchangeable evidence.
- Quiz legacy API compatibility changes state semantics. Course totals, assignment grades, quiz-attempt grades, gradebook outcomes, and competencies must not be flattened into one generic assessment result.
- `docs.moodle.org/500/en/Web_services` returned 403 and was not treated as read evidence. Several older guessed external-source paths returned 404, including `completion/externallib.php`, `mod/quiz/externallib.php`, and `grade/report/user/externallib.php`; their actual pinned classes are linked above. `report/log/externallib.php` and guessed assignment exporter files also returned 404 and do not establish a log or exporter contract.
- Validation performed: non-truncated pinned tree inspected; all 84 XMLDB files parsed; one test-fixture schema excluded; 487 unique non-test table names and 4,430 database field rows retained from 83 files; CSV round-trip/uniqueness/nullability/date checks passed; `assign_submission`, `quiz_attempts`, and `logstore_standard_log` field sets re-compared with official XML. The actual Silver workbook's 28 tables and 345 columns were read without modification.
- Remaining blockers: no live version/plugins/services/API documentation, no credentials or approved database export, no authorized sample records, no verified retention/history, and no approved privacy/cross-source mapping rules. No percentage coverage in existing research should be treated as a tenant-readiness measure.
