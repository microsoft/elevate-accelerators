# Primary District Sample Data

This package is sufficient to start **file-based engineering tests without Docker, tenants, or real student data**. It was generated by project code using the captured official schemas, not by vendor tools and not by a running LMS. All people, identifiers, schools and results are fictional.

## Files and execution

- The [district profile](District%20Profile.md) is now the **primary and only active sample dataset**: three schools, 1,800 current students, 103 teachers and two school years of 180 instructional days each by default, with deterministic varied behavior and fictional names.
- Source folders below contain **one CSV per table**: 28 source datasets only. They replace the previous 30-student files at the same paths. No precomputed cross-source mapping tables are ingestion inputs.
- [manifest.json](manifest.json): profile assumptions, source/entity/interface/grain, relative CSV paths, row counts, column names, SHA-256 hashes, evidence hashes and expected metrics. This is test metadata, not vendor data.
- [generate.py](generate.py): primary command delegating to [generate_district.py](generate_district.py). Both commands generate/check the same district tables in this directory; neither recreates the small dataset.
- The old combined JSON and small-only Moodle module/completion tables have been removed. Load CSVs listed in the manifest, not old cached files or the retired ignored `generated/district/` location. Historical small fixtures remain recoverable from Git history.

### CSV encoding

- UTF-8, comma-delimited, LF line endings; CSV quoting handles commas, quotes and JSON array contents.
- `\N` represents null. Empty text remains an empty cell. Configure the reader's null token explicitly; do not treat every empty cell as null.
- Booleans use `true` / `false`; numeric fields use JSON numeric notation. Arrays/objects use JSON within a quoted CSV cell, such as Canvas `submission_types`.
- The manifest lists **column names**, not vendor types or nullability. Unlike the retired small manifest, `columns` is a list rather than a type-description object. Define types in the ingestion contract and preserve external identifiers and grade labels as text instead of trusting spreadsheet inference.
- These are selected-field fixtures; a missing column does not imply that the vendor does not support it. Every generated row has the declared number of columns.

These CSVs are an inspectable projection of our synthetic package, not certified native vendor exports. Canvas files remain REST-shaped selections, not SIS import files; Moodle files remain selected XMLDB fields. Original interface limitations below still apply.

Run from the accelerator folder (`education/education-analytics`):

```powershell
python "sample-data/generate.py"
python "sample-data/generate.py" --check
```

Requires Python 3.11+ with no third-party packages. Generation overwrites the primary manifest and listed CSVs in this directory; it does not create a combined JSON or delete unrelated files. Check mode validates hashes, row counts, selected relationships and expected metrics, and rejects missing or extra CSV tables in the four primary source folders, including stale CSVs if the removed Shared folder is reintroduced. Fixed dates and identifiers make reruns reproducible. Evidence hashes are recorded in the manifest. The primary CSVs replace the existing version-controlled samples and are not ignored; only the retired `generated/` location remains ignored.

For a custom volume, run `python "sample-data/generate.py" --schools 3 --average-students-per-school 600 --days 180`. Individual school populations vary around the supplied average while preserving the requested total. The former `--students-per-school` spelling remains an alias. Generation replaces the primary profile; it does not create a second copy. Check mode uses the saved manifest, not sizing flags.

## Cohort and known answers

The fictional Cedar Valley School District has 1,800 grade-6-to-8 learners across three unequally sized schools, with six subjects per learner. School 1 uses Moodle and schools 2-3 use Canvas. The fictional institutions carry full addresses at real Snohomish County, Washington localities — Everett 98201, Lynnwood 98036 and Edmonds 98026 — with synthetic street numbers, so a map geocodes them without naming a real building. All three have PowerSchool-shaped and NWEA-shaped records. Population, LMS, and attendance ordering are deliberately not aligned, but this fixture is not evidence of an LMS effect. This allocation is a generator assumption recorded in the manifest, not a supplied mapping CSV. No institution or tenant is needed; personal and institution names are fictional and emails use reserved `.example` domains.

Attendance uses deterministic hash-based draws with school, learner, weekday, season, and grade effects, plus a **year-long pattern per learner** (see below); it is reproducible without repeating one arithmetic cycle across schools. Assignments are built the same way: how many tasks a class sets, which of the six formats each one is, what total it is marked out of (10 to 120 points) and when it is due are four independent seeded properties, so no class, format or week is interchangeable with another. Because mark schemes differ, the coursework measure must divide summed points by summed maxima rather than average per-task percentages. Marks are a learner's general standing, a per-learner **per-subject** aptitude, a per-topic offset within each subject, how severely the subject marks and how demanding the task format is, scaled to that task's own scheme. Missing and late work are drawn against the same per-subject standing, so gaps in what was handed in fall where the marks are weakest. All score changes remain deliberately constructed arithmetic, **not NWEA normed growth, vendor-projected growth, proficiency, or evidence of intervention effectiveness**. No norms, percentiles, linking-study levels, growth-eligibility flags or real historical observations are fabricated. Fall/winter/spring dates and labels are simulation choices. The 540/600/660 school sizes and 180-day calendar are engineering assumptions, not measured averages or an actual district schedule.

Moodle completion is **not represented** in this profile; do not carry forward the old 80% completion expectation. Moodle attempt numbering starts at zero; Canvas submitted attempts use one. Missing Canvas work has null attempt/time/score; missing Moodle work has a `new` state and no grade record. These are explicit fixture conventions, not universal vendor behavior.

## Change over the year and teacher actions

A real district's records are not static: attendance changes during the year, absence shows up in coursework and tests, and teachers record what they did about it. The default data carries these patterns for everyone, so the same files support everyday reporting and following a figure from the district down to a single learner. There is no separate demo mode.

- **Year-long attendance patterns.** About 70% of learners keep a steady pattern. About 15% have a mid-year dip starting between November and January, 8% decline gradually and 7% improve.
- **Absence reaches the work.** Work due after absences in the two school weeks before it is more often missing or late and is marked lower. RIT growth between test sittings is smaller when more days were missed in between.
- **Transparent early-warning rules**, not risk scores: *5 or more absences in 20 school days* and *3 or more of the last 5 pieces of work missing in one class*.
- **Teacher action log** ([log_entries](PowerSchool/log_entries.csv)). When a rule is met, an action is logged in about 75% of cases, one to four days later. Attendance actions are logged by one core-subject teacher per learner and escalate: check-in, family contact, attendance plan, counselor referral. Missing-work follow-ups are logged by that class's teacher. Each action has a follow-up after 10 school days with a descriptive outcome note read from the records. Actions whose follow-up falls after the last day stay `Open`.
- **Missing work persists until it is followed up.** Once the missing-work rule is met in a class, the learner keeps missing more work there until a follow-up they respond to.
- **Both outcomes are present.** About 60% of actions are followed by fewer absences or less missing work in that class, and the rest are not. Some learners meet the rule and get no action at all. A learner never gets two follow-ups of the same kind on one day, so their first one is unambiguous.

The share of actions followed by improvement is a **constructed assumption**, not evidence that an action works. Because the rule selects a window with unusually many absences, part of any before/after drop is regression to the mean; a report should say "observed after", not "caused by".

## Two school years

Real reporting compares years, and membership changes between them. The sample therefore carries the previous school year (2024-2025) as well as the current one (2025-2026), in the shape many SIS exports use:

- [terms](PowerSchool/terms.csv) lists the school years with their first and last instructional day.
- [enrollments](PowerSchool/enrollments.csv) is the current year's membership, with the year group on the student record. [reenrollments](PowerSchool/reenrollments.csv) holds earlier years' membership with the year group then, as PowerSchool's reenrollments table does.
- [students](PowerSchool/students.csv) includes **former learners** (`Inactive`) who were enrolled last year but not this year, with the school and year group they were last in.
- Learners now in grades 7 and 8 were one grade lower last year, except about 6% who joined this year; about 3% were at another of the district's schools. This year's grade 6 arrived from elementary school. Last year's grade 8 moved on, and about 5% of grades 6 and 7 left the district.
- Last year has its own attendance (the same learner risk, a separately drawn year-long pattern and a different baseline per school) and its own Fall, Winter and Spring tests. Class rosters, LMS coursework and the action log start this year, as they would once last year's LMS courses are archived.

## Silver use

Bronze ingestion should consume only the four source folders. The manifest describes test files and expected metrics; it is not a fifth source or a Silver mapping table. The removed Shared CSVs are neither generated nor required.

During Bronze-to-Silver transformation, derive identity links from PowerSchool `student_number`, Canvas `sis_user_id`, Moodle `idnumber` and NWEA `StudentID`, qualified by the ingestion source instance. Persist canonical identities and mappings in Silver rather than reading a precomputed sample crosswalk. Missing or ambiguous identifiers must be explicit exceptions, not guessed name/email matches.

The current validator derives temporary source-qualified student lookups in memory, using student enrollments to exclude Canvas teacher accounts and Moodle user enrollments to select learners. It checks source-to-SIS matches and rejects duplicate or unresolved identifiers. This is validation code, **not an implemented or persisted Silver transformation**. The fixture assumes one instance per source and fixed school membership within each school year; future transformations must handle their declared time/instance scope.

Source-instance registration comes from version-controlled pipeline configuration. Observed school/source coverage can be derived from incoming relationships; expected coverage must be configured to detect missing feeds. None requires manually entered mapping rows, but configuration cannot be inferred reliably from an empty source extract.

Start with identity, school/course/class mappings, enrollment, attendance, learning content, assignment submission and assessment-result transformations. Derive expected attendance from calendar plus effective school membership; do not equate minutes absent with attended minutes. Keep RIT separate from percentages and preserve raw source identity.

This package does **not** fill all 28 tables of the research Silver register. Proposed SIS teacher relationships, Canvas teacher enrollments and teacher-logged student actions are included; the action log is shaped to feed the recommended `InterventionAction` and `ActionType` entities (learner, school, class, teacher, type, reason, status, follow-up date, completed date, outcome note), and `EDU_BR_SL_Transform` now publishes them; Gold carries them as `FactStudentAction`. Moodle staff roles, completion, status histories, activity logs, assignment overrides, guardian data, standards alignment and structured assessment outcomes are not included. Do not interpret omitted datasets as zero activity. It does not establish higher-education coverage.

## Checks performed

Generation checks selected source field names against captured evidence and row widths. Validation checks the exact manifest table set, file hashes, headers and counts, student/class/school relationships, composite attendance/submission keys, test-event uniqueness, late/missing conventions, score bounds, subject variation, school addresses against the declared real localities, disjoint student and staff given-name and surname pools, assignment variation across count/mark scheme/format mix/due-date calendar, year-long attendance patterns, every logged action (learner, class and teacher belong together; the cited rule was met in the days before; the outcome note matches the records), the before/after follow-up figures for attendance and coursework, the link between absence and missing work, both school years (every attendance and test row inside a membership, former learners, prior-year rates by school and the enrollment movement between years), and expected metrics. Every recorded metric, including the per-subject scores, the mean within-learner subject spread and the assignment breakdown, is recomputed from the CSVs and compared exactly, so the manifest cannot describe data that is no longer there. The district validator does not provide full vendor primitive-type/nullability validation or reconstruct every CSV cell to its original type.

These are **fixture checks**, not Silver transformation tests: no Bronze/Silver/Gold pipeline has been executed. The expected results are the assertions that future transformations should satisfy. Production permissions, API paging, full source constraints, partial failures and vendor-runtime behavior are not tested here.
